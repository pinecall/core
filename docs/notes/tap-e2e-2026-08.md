# `knowledge tap` end-to-end — 2026-08-16

A real proof run of the built CLI (`node dist/cli.js`) against a real site and a
real org knowledge base. Not a unit test: this one hits the network on purpose.

- Site: <https://bernardocastro.dev> (sitemap has exactly one URL)
- Build: `npm run build`, clean
- Auth: `PINECALL_API_KEY` from the environment — no key appears anywhere below
- KB created and deleted within the run; org left as it was found

Output is trimmed (ANSI stripped, progress bar collapsed) but nothing was
rewritten.

## Conclusions

**Timings.** Dry-run 2.6 s · full tap into a new KB 4.5 s · sync 3.4 s. All of
it is network latency; the crawl of a one-page site is free. Retrieval was
queryable within ~10 s of the tap returning, so the "reindex is async, retry for
60 s" caution did not bite once. Do not read that as a guarantee — one page is
the smallest possible index, and a forty-page tap may well need the wait.

**Surprises, in order of how much they matter.**

1. *The manifest is a retrieval candidate.* `_tap-manifest.json` scored 0.837 on
   a content question and took a slot in the top four. On a one-page KB that is
   cosmetic; on a small KB with a `topK` of 4 or 5 it costs a real chunk of
   answer. The knowledge API has no "store but do not index" flag
   (`KnowledgeDocInput` is `{ path, title, text }`), and this milestone forbids
   server changes, so there is no fix available from the client side today.
   Worth a server-side `indexed: false` later; until then, a caller who cares
   should raise `topK` or filter hits whose `doc_path` is the manifest.
2. *One-page site is a thin proof.* bernardocastro.dev genuinely has a
   single-URL sitemap, so this run never exercised concurrency, the link
   fallback, the page limit, `needsJs` flagging, or a partial-failure batch.
   Everything asserted here is real, but the multi-page paths remain covered
   only by unit tests. A second e2e against a bigger site would be cheap and is
   the obvious follow-up.
3. *A pluralization bug, fixed in this card.* The zero-delta line read
   "1 pages unchanged". Fixed in `src/cli/commands/knowledge.ts` and reported on
   tk-1e0cea; the pty run above shows the corrected wording.

**What did not go wrong.** No 4xx, no partial push, no manifest drift, no
stale-hash false positive on the immediate sync, and the frontmatter survived
extraction into the chunk text intact — which is what makes a cited answer
possible.
